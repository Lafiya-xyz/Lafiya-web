## Issue #857: Four-Eyes Rule for Destructive Operations

### Problem Statement

**Current State:**
- Destructive operations executed by single operator
- No approval workflow for high-risk actions
- Insider error or compromised account = irreversible harm
- No prevention of bait-and-switch attacks

**High-Risk Operations:**
- Bulk capability revocation
- Payout kill-switch overrides
- Attester allowlist changes
- Patient data deletion
- Bulk account suspension
- Financial adjustments
- Emergency access grants
- Audit log purges

**Attack Scenarios:**
1. **Insider Threat:** Disgruntled employee revokes all provider capabilities
2. **Account Compromise:** Attacker gains single operator account, triggers unauthorized actions
3. **Bait-and-Switch:** Operator proposes legitimate action, swaps payload before execution
4. **Error Cascade:** Mistaken bulk deletion affects thousands of patients

**Impact:**
- Critical: Single point of failure for destructive operations
- Compliance: Violates SOC 2 segregation of duties
- Financial: Unauthorized actions could cause significant harm

### Technical Analysis

**Four-Eyes Principles:**
1. **Separation of Duty:** Proposer ≠ Approver
2. **Time-Bound:** Proposals expire after configurable period
3. **Immutable Hash:** Payload hash verified at execution time
4. **Full Audit:** Every proposal, approval, rejection, expiry logged
5. **Role-Based:** Only specific roles can propose/approve specific actions

**Proposal Lifecycle:**
```
1. Propose    → Operator A submits action with justification
2. Review     → Operator B (different person) reviews proposal
3. Approve    → Operator B approves with signature
4. Execute    → System verifies hash match, executes action
5. Audit      → Full trail recorded (who, what, when, why)
```

### Implementation Plan

**Key Components:**
1. Database schema for proposals and audit logs
2. FourEyesService class for proposal management
3. API routes for proposal operations
4. Admin UI for review and approval
5. Background job for expiring old proposals

**Database Schema:**
- `operator_proposals` table with status tracking
- `proposal_audit_log` table for lifecycle events
- `operator_permissions` table for role-based access
- Constraints ensuring different proposer/approver

**Service Methods:**
- `proposeAction()` - Create proposal with hash
- `approveProposal()` - Approve with validation
- `rejectProposal()` - Reject with reason
- `executeProposal()` - Execute with hash verification
- `cancelProposal()` - Cancel by proposer
- `expireOldProposals()` - Background cleanup

**Security Features:**
- SHA-256 hash of canonical JSON payload
- Hash verification at execution prevents bait-and-switch
- DB constraint: `reviewed_by != proposed_by`
- RLS policies enforce permissions
- Full audit trail with IP and user-agent

### Testing Strategy

**Unit Tests:**
- Proposal creation with hash generation
- Approval by different operator
- Rejection of same-operator approval
- Bait-and-switch detection via hash mismatch
- Proposal expiry workflow
- Role permission enforcement

**Integration Tests:**
- Complete propose → approve → execute flow
- Rejection workflow
- Cancellation workflow
- Expiry background job
- Audit log completeness

### Acceptance Criteria

- [ ] Operator proposals schema created
- [ ] FourEyesService implements all lifecycle methods
- [ ] Hash verification prevents bait-and-switch
- [ ] Proposer and approver must be different
- [ ] Role-based permissions enforced

## Issue #858: ReDoS Audit - Eliminate Catastrophic Backtracking

### Problem Statement

**Current State:**
- Regular expressions applied to attacker-controlled input
- No systematic audit of regex complexity
- No input length bounds before regex evaluation
- Potential for catastrophic backtracking = denial of service

**Vulnerable Pattern Example:**
```typescript
// VULNERABLE: Catastrophic backtracking
const EMAIL_REGEX = /^([a-zA-Z0-9]+)*@([a-zA-Z0-9]+)*\.([a-zA-Z]{2,})$/;

// Attack: "aaaaaaaaaaaaaaaaa!" causes exponential time
// Each additional 'a' doubles evaluation time
```

**Attack Scenarios:**
1. **Route Handler DoS:** Malicious input to validation endpoint
2. **User-Agent Parsing:** Crafted UA string causes timeout
3. **Phone Validation:** Long repeated digits exhaust CPU
4. **Locale Parsing:** Crafted locale string causes hang

**Impact:**
- Critical: Cheap DoS on serverless functions
- Availability: Single request can consume 100% CPU
- Cost: Excessive serverless execution time

### Technical Analysis

**Regex Complexity Classes:**
1. **Constant O(1):** Fixed-length patterns
2. **Linear O(n):** No backtracking
3. **Polynomial O(n²):** Limited backtracking
4. **Exponential O(2ⁿ):** Catastrophic backtracking ⚠️

**Vulnerable Patterns:**
- Nested quantifiers: `(a+)+`, `(a*)*`
- Overlapping alternation: `(a|a)*`, `(a|ab)*`
- Ambiguous groups: `(.*).*`

**ReDoS Detection Tools:**
- `eslint-plugin-regexp` - ESLint integration
- `safe-regex2` - JavaScript analysis
- `recheck` - Rust-based static analysis (most accurate)

### Implementation Plan

**Key Components:**
1. ESLint configuration with regexp rules
2. Automated regex audit script
3. Safe regex wrappers with input bounds
4. Refactoring of vulnerable patterns
5. CI integration for continuous testing

**ESLint Rules:**
- `regexp/no-super-linear-backtracking` (error)
- `regexp/no-misleading-capturing-group` (error)
- `regexp/no-useless-quantifier` (error)
- `regexp/optimal-quantifier-concatenation` (warn)

**Safe Regex Wrappers:**
- `safeMatch()` - with length bounds
- `safeTest()` - with length bounds
- `safeReplace()` - with length bounds
- `validateRegex()` - compile-time validation

**Mitigation Strategy:**
1. Static analysis to detect vulnerable patterns
2. Input length bounds (reject > N chars before regex)
3. Regex rewriting to eliminate nested quantifiers
4. Fuzzing to test worst-case inputs

### Testing Strategy

**Fuzzing Tests:**
- Worst-case inputs for each pattern
- Performance benchmarks (<10ms per match)
- Length bound rejection tests

**CI Integration:**
- ESLint runs on all PRs
- Audit script fails on exponential complexity
- Performance regression tests

### Acceptance Criteria

- [ ] ESLint regexp plugin configured
- [ ] Audit script extracts all patterns
- [ ] CI fails on exponential/polynomial complexity
- [ ] Safe regex wrappers implemented
- [ ] Input length bounds enforced
- [ ] All vulnerable patterns refactored
- [ ] Email validation uses safe pattern
- [ ] Phone validation uses safe pattern
- [ ] User-agent parsing bounded
- [ ] Fuzzing tests cover worst-case inputs
- [ ] Performance benchmarks pass

## Issue #859: Harden JSON Body Parsing

### Problem Statement

**Current State:**
- Route handlers call `request.json()` directly
- No uniform size cap on request bodies
- No nesting depth limit
- No array length limit
- No protection against prototype pollution

**Vulnerable Code:**
```typescript
// CURRENT: No limits
export async function POST(request: Request) {
  const body = await request.json(); // ⚠️
  // Could be 100MB, deeply nested, or prototype pollution
}
```

**Attack Scenarios:**
1. **Memory Exhaustion:** 100MB JSON payload
2. **Stack Overflow:** Deeply nested object (1000+ levels)
3. **CPU Exhaustion:** Array with 1 million elements
4. **Prototype Pollution:** `{"__proto__": {"isAdmin": true}}`
5. **Zip Bomb:** Compressed JSON expands huge

**Impact:**
- Critical: Serverless crashes, cold starts, high costs
- Security: Prototype pollution enables privilege escalation
- Availability: DoS via large/complex payloads

### Technical Analysis

**JSON Parsing Limits:**
- Max body size: 64 KiB (configurable)
- Max depth: 10 levels
- Max array length: 1000 elements
- Max string length: 10,000 chars
- Max object keys: 100 per object
- Prototype keys: Blocked (`__proto__`, `constructor`, `prototype`)

**Prototype Pollution:**
```typescript
const payload = {"__proto__": {"isAdmin": true}};
const user = {...payload};
console.log({}.isAdmin); // true (polluted!)
```

### Implementation Plan

**Key Components:**
1. `parseJsonBody()` helper with all limits
2. Streaming size enforcement (abort early)
3. Structure validation (depth, array length, etc.)
4. Prototype key removal
5. Zod schema integration

**parseJsonBody Features:**
- Streams body with byte cap
- Validates structure limits
- Removes dangerous keys
- Zod schema validation
- Custom error types

**Route Migration:**
- Replace all `request.json()` calls
- Add Zod schemas for each route
- Configure per-route limits
- Add appropriate error handling

### Testing Strategy

**Unit Tests:**
- Valid JSON parsing
- Size limit enforcement
- Depth limit enforcement
- Array length limit
- Prototype key removal
- Zod validation

**Integration Tests:**
- Route accepts valid payloads
- Route rejects oversized payloads
- Route handles prototype pollution
- Error responses have correct status codes

### Acceptance Criteria

- [ ] `parseJsonBody` helper implemented
- [ ] Streaming size limit enforced
- [ ] Nesting depth limit enforced
- [ ] Array length limit enforced
- [ ] Object key count limit enforced
- [ ] String length limit enforced
- [ ] Prototype keys removed
- [ ] Zod integration complete
- [ ] Custom error types defined
- [ ] All routes migrated

## Issue #860: Regression Tests for Next.js Vulnerabilities

### Problem Statement

**Current State:**
- Framework updates don't include vulnerability regression tests
- Configuration changes can reintroduce bugs
- No systematic testing of known attack vectors

**Known Next.js Vulnerability Classes:**
1. **Middleware/Proxy Bypass:** Internal headers bypass auth
2. **Cache Poisoning:** RSC/HTML variants cached incorrectly
3. **SSRF via Host Header:** Server Actions use Host for fetch
4. **Image Optimizer Abuse:** Arbitrary URL fetching
5. **Redirect Open Redirect:** Unvalidated redirect targets

**Attack Examples:**
```
1. X-Middleware-Subrequest: 1 → Bypass auth
2. Accept: text/x-component → Cache poisoning
3. Host: internal.service → SSRF in Server Actions
4. /api/image?url=http://169.254.169.254/ → AWS metadata
5. redirect(query.next) → Open redirect to evil.com
```

**Impact:**
- Critical: Auth bypass, SSRF, information disclosure
- Security: Framework upgrades may reintroduce bugs
- Compliance: Need proof of vulnerability testing

### Technical Analysis

**Vulnerability Categories:**
1. **Header Injection:** Internal headers, Host manipulation
2. **Cache Attacks:** Variant confusion, key poisoning
3. **SSRF:** Image optimizer, Server Actions
4. **Redirect Issues:** Open redirects, protocol confusion
5. **Response Splitting:** CRLF injection

**Testing Strategy:**
- Production build testing (not dev mode)
- Automated regression suite
- Known CVE reproduction
- Configuration validation

### Implementation Plan

**Key Components:**
1. Security regression test suite
2. Proxy bypass tests
3. Cache poisoning tests
4. SSRF prevention tests
5. Redirect validation tests
6. CI integration

**Test Categories:**

**A. Proxy/Middleware Bypass:**
- Send `x-middleware-subrequest: 1` to protected routes
- Verify auth still applies
- Test other internal headers
- Validate proxy.ts protections

**B. Cache Poisoning:**
- Request RSC variant (`RSC: 1`)
- Request HTML variant (normal)
- Verify different cache keys
- Test Next-Router-State-Tree header

**C. SSRF Prevention:**
- Test Host header in Server Actions
- Test image optimizer URL validation
- Verify internal IP blocking (169.254.*, 10.*, 192.168.*)
- Test DNS rebinding protection

**D. Redirect Validation:**
- Test redirect with external URLs
- Test protocol-relative URLs (`//evil.com`)
- Test javascript: protocol
- Test data: URIs
- Verify allowlist enforcement

**E. Configuration Validation:**
- Verify security headers present
- Check CSP configuration
- Validate CORS settings
- Test rate limiting

### Testing Strategy

**Test Structure:**
```typescript
describe('Next.js Security Regression', () => {
  beforeAll(async () => {
    // Start production build
    await startProductionServer();
  });

  describe('Proxy Bypass', () => {
    it('should not bypass auth with x-middleware-subrequest');
    it('should not bypass auth with x-nextjs-data');
  });

  describe('Cache Poisoning', () => {
    it('should cache RSC and HTML separately');
    it('should not poison cache with custom headers');
  });

  describe('SSRF Prevention', () => {
    it('should block internal IPs in image optimizer');
    it('should validate Host header in Server Actions');
  });

  describe('Redirect Validation', () => {
    it('should block external redirects without allowlist');
    it('should block javascript: protocol');
  });
});
```

**CI Integration:**
- Run against production build
- Test on every framework upgrade
- Test on configuration changes
- Fail CI on any vulnerability
